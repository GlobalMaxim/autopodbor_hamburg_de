# Админ-панель — техническое описание

Источник: `admin-panel.txt` (исходные заметки заказчика). Ниже — технический разбор: что это значит в терминах архитектуры проекта, как реализовать, какая инфраструктура для этого нужна и сколько это весит по сложности.

## Ключевой момент архитектуры

В `architecture.md` уже выбран **Payload CMS + PostgreSQL** как CMS-слой. Это меняет расклад: Payload **сам генерирует админ-панель** из описания коллекций (полей, типов, валидации) — это не «построить UI с нуля», а «описать схему данных конфигом». Экран со списком отзывов, формой добавления, загрузкой файлов, валидацией — всё это Payload рисует сам.

Из этого следует: самая объёмная часть задачи — не сама админка, а **инфраструктура, которой сейчас нет вообще**:

- Payload-сервер (Node.js), отдельно от Vercel-фронтенда (Vercel не держит постоянный процесс)
- PostgreSQL (managed — Neon/Supabase/Railway)
- S3-совместимое хранилище для фото/видео — Cloudflare R2, уже заложен в `architecture.md`
- Почтовый провайдер для писем подтверждения (Resend/Postmark/SMTP) — сейчас нет вообще
- Хостинг Payload-процесса (VPS/Railway/Fly.io)
- Подключение фронтенда к Payload API вместо текущих mock-данных (`lib/content.ts`)

Ничего из этого списка в проекте пока не поднято. Все 4 пункта ТЗ *зависят* от этой инфраструктуры — она делается один раз, а не per-фича.

## 1. Отзывы (Review)

Расширение уже описанной в `architecture.md` коллекции `Review`.

**Поля:**
```
text        — richtext/textarea, текст отзыва
rating      — number (1–5)
date        — date
source      — select: Google / Telegram / TikTok / другое (уже было)
mediaType   — select: image | video | tiktokLink
photo       — upload (Media), видно если mediaType = image
video       — upload (Media), видно если mediaType = video
tiktokUrl   — text (URL, валидация формата ссылки), видно если mediaType = tiktokLink
published   — checkbox
```
Условная видимость полей (`admin.condition` в Payload) — показываем нужное поле в зависимости от `mediaType`, не плодим три отдельные формы.

**Сложность:** низкая — конфиг одной коллекции поверх уже поднятого Payload.

## 2. Кейсы (Case)

Тут почти всё **уже описано** в `architecture.md` (`title, slug, brand, model, year, mileage, price, engine, transmission, verdict, clientTask, process, inspection, findings, decision, result, photos[], videos[], published`). Заметки из `admin-panel.txt` по сути подтверждают этот же набор:

- «статус» = уже существующий `verdict` (🟢/🟡/🔴)
- «заголовок, год, пробег, коробка, объём мотора» = `title/brand/model`, `year`, `mileage`, `transmission`, `engine`
- «описание» = `clientTask/process/findings/decision/result`
- «фото/видео» = `photos[]`/`videos[]` (upload-массивы)

**Сложность:** низкая — это не новая функциональность, а реализация уже спроектированной коллекции. Единственное, чего действительно не было в текущем mock-е (`lib/content.ts`) — поля `photos`/`videos` физически отсутствуют в типе `Case`, это уже отмечено как пробел в `ROADMAP.md`.

## 3. Видео-примеры отчётов в блоке «Как это работает»

Это **новая** сущность, в `architecture.md` её не было. Нужна отдельная коллекция, например `ReportExample`:

```
title       — text (подпись примера)
step        — number/select — к какому шагу процесса относится (опц.)
media       — upload (video, опц. + превью-картинка/постер)
order       — number, порядок показа
published   — checkbox
```

На фронтенде — новый блок на `/how-it-works` (и, возможно, превью на главной рядом с `HowItWorks`), читающий эту коллекцию через Payload API вместо статичного списка шагов.

**Сложность:** низкая-средняя — новая коллекция + новый UI-блок на фронте. Отдельный нюанс: **видео тяжелее фото на порядок** — стоит сразу заложить лимит размера загрузки и, возможно, сжатие/транскодинг (Payload сам не транскодирует, нужен либо ручной процесс, либо сторонний сервис типа Cloudflare Stream, если видео должны воспроизводиться быстро на мобильных).

## 4. Регистрация с подтверждением по email

Технически — включается на уровне коллекции `Users` в Payload: `auth: { verify: true }` даёт email-подтверждение из коробки, но это работает для **одной** auth-коллекции с единой логикой доступа. Чтобы разделить «админ» и «обычный пользователь без доп. функций», нужно:

- поле `role: 'admin' | 'customer'` в `Users`
- access-control правила Payload: доступ к админ-панели (`/admin`) только у `role: admin`
- отдельная **публичная** форма регистрации на фронтенде (её сейчас нет вообще — это не Payload admin UI, а страница на самом сайте)
- страницы подтверждения email / логина / (скорее всего) восстановления пароля — тоже на фронтенде
- настроенный email-провайдер для писем подтверждения

**Сложность:** средняя. Не потому что Payload не умеет — умеет из коробки, — а потому что «завести обычных пользователей» тянет за собой полноценный UX (форма регистрации, подтверждение, логин, сообщения об ошибках) на **фронтенде**, которого сейчас нет ни в каком виде.

### ⚠️ Расхождение с исходным ТЗ

`technical-description.txt`, финальный раздел, п.17 «Что НЕ делать» прямо перечисляет: **«без… личных кабинетов, регистрации/авторизации»**. Новая задача из `admin-panel.txt` (обычные пользователи с регистрацией) этому прямо противоречит. Это не блокер — просто нужно осознанное решение: либо это изменение объёма проекта (тогда стоит обновить `architecture.md`/ТЗ), либо регистрацию стоит ограничить только админом/сотрудниками (без публичной формы для клиентов) — тогда сложность падает до низкой (это просто `auth: true` на `Users`, без фронтенд-форм).

## Итоговая оценка сложности

| Блок | Сложность | Почему |
|---|---|---|
| Инфраструктура (Payload + Postgres + R2 + email + хостинг) | **Средняя, разовая** | Ничего из этого не поднято; после того как сделано один раз — все 4 пункта становятся дешёвыми |
| Отзывы | Низкая | Конфиг коллекции поверх готовой инфры |
| Кейсы | Низкая | Уже спроектировано в architecture.md, почти no-op |
| Видео-примеры "Как это работает" | Низкая-средняя | Новая коллекция + новый блок на фронте, видео тяжелее фото |
| Регистрация с подтверждением | Средняя (если публичная) / Низкая (если только админ) | Зависит от решения по конфликту с ТЗ выше |

**Главный вывод:** сама «админка» — не тяжёлая часть (Payload генерирует её из конфига). Тяжёлая часть — поднять backend-инфраструктуру, которой в проекте сейчас нет вообще (сервер, БД, хранилище, почта). Это разовая инвестиция уровня «фаза 2 MVP» из `architecture.md`, а не мелкая доработка поверх текущего Next.js-фронтенда с mock-данными.
